# Engineering rules для агентов (детали к AGENTS.md)

## 1. Структурный фикс вместо словаря
Принцип и аудит — [cr-eliminate-lexical-semantic-hardcoding.md](../cr-eliminate-lexical-semantic-hardcoding.md).
Порядок выбора фикса:
1. Модель выбирает из закрытого набора: `Literal`/enum, ID из каталога хода (каст, места, предметы, выходы).
2. Инвариант в БД (уникальный индекс, FK, одна текущая запись на `(subject_id, type)`).
3. Проверка графа/authority в детерминированном коде.
Запрещено: словари глаголов/падежей, `token[:4]`, сравнение имён по тексту, генерация «Имя 2»,
пост-фильтры прозы по словам. Разрешено (по CR): распознавание письменности, структурные шаблоны
собственного вывода (UUID, технические токены).

PR-чек: diff удалил больше веток/списков, чем добавил? Если код вырос — объясни в описании PR почему.

## 2. Канон и проза
- Источник истины: типизированный исход плана → `TurnAuthority` → запись в БД. Narrator лишь рендерит
  ([narration-pipeline.md](../architecture/narration-pipeline.md), [ADR-007](../adr/007-turn-pipeline-and-knowledge-boundary.md)).
- Валидатор ловит только четыре запрета (`four_bans_only`). Всё остальное — свобода мастера.
- Новый факт заменяет старый по `(subject_id, type)`. Текстовый субъект — дыра (см. sim300-night: 71/101).
- Различия мастеров (политика инициативы, каталог приёмов) — данные мастера, а не общий код.
  Повторы гасятся структурно (ID приёма, запрет повтора подряд), не баном фраз.

## 3. Тесты
Слои и хорошие/плохие assert — [TESTING-STRATEGY.md](../TESTING-STRATEGY.md). Дополнительно:
- Red first: в PR указать, что тест падал на `main` до фикса.
- Каждый новый тест должен убивать конкретную мутацию (перевернуть `if`, удалить вызов) в целевой ветке.
- Запрещённые формы: `assert "..." in prompt`, чтение `.py`-исходника, `mock.assert_called*` как
  единственная проверка, тест без assert. Существующие такие тесты удаляются или переписываются.
- Тесты, закрепляющие баг (новая сцена на каждый возврат, «Служанка 2», матч фактов по тексту),
  переписываются в том же PR, что и фикс.
- Гигиена: без зависимости от cwd (пути от `Path(__file__)`), без import-time мутации промптов
  (сейчас: `*_guard.py` в `services/`), без зависимости от порядка запуска (`pytest -p randomly` полезен).
- Сага/откат: наблюдать результат отдельной `AsyncSession`, иначе харнесс прячет commit/rollback.
- SQLite lock: два engine на один файл, фоновый писатель держит транзакцию; не `AsyncMock(side_effect=OperationalError)`.

## 4. Мутационное тестирование
- Раннер: собственный AST (mutmut 3.x несовместим с набором). Сейчас лежит вне репо
  (`/workspace/mutrun/gen.py`, `run.py`) — **предлагается перенести в `scripts/mutation/`**.
- Охват: 11 модулей ядра, 2157 мутантов, ~45 мин на 8 воркерах. Базовая линия (2026-10, до P0):
  fact_repo 78, action_plan_compiler 71, turn_authority_validator 69, turn_planner 59,
  turn_authority_service 57, name_identity_contract 47, scene_transition_executor 47, turn_saga 32 (%).
- Правило: PR в модуль ядра не опускает его score; цель для ядра ≥70%, для turn_saga — рост до 60% в первую очередь.
- Гонять раз в неделю и перед soak-прогоном; результат класть рядом с отчётом прогона.

## 5. Плейтест и soak
Протокол и causal trace — [playtest-protocol.md](../playtest-protocol.md).
- Ручная игра: один ход → прочитать ответ и debugger-trace → следующий ход. Драйвер-скрипты, батчи и
  параллельная отправка запрещены: они не видят ответ и портят ритм сцены.
- Изоляция: свой `data dir`, свой порт, копия ChatGPT-профиля. Основной сервер/профиль не трогать.
- Soak (сотни ходов): сервер как отдельная служба (не дочерний процесс сессии агента),
  watchdog по `/health` + алерт при отсутствии хода > N мин, снапшот БД каждые 50 ходов,
  метрики: `python scripts/soak_metrics.py <backup.db>`.
- Отчёт обязателен: коммит, s/ход, $/ход, input tokens по полусотням, доля кэша, падения/ремонты по
  причинам, сцен на место, дубли сущностей, противоречия фактов, первая неправильная граница.
