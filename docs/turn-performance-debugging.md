# Куда ушло время хода

Открыть `/api/debugger`, выбрать кампанию, раскрыть блок «Куда ушло время хода».
Подробные замеры появляются для новых попыток после обновления приложения.
Для старых ходов отсутствующее разложение не восстанавливается задним числом.

## Границы и расчёт

Каждая попытка имеет `trace_id`, ID исходного пользовательского хода, `generation_run_id`.
Возобновление того же хода создаёт новую трассу, не затирая предыдущую.
Сводка сохраняется как `generation_decisions.step=performance` через существующий
независимый буфер телеметрии после транзакции хода. Миграция БД не требуется.
Успешные, неуспешные и отменённые попытки сохраняются одинаково.

Полное время начинается при входе в сагу и заканчивается готовностью ответа после
публикации либо обработки ошибки/отката. Доставка ответа клиенту, фоновая память и
финальная запись самой телеметрии в это время не входят.

Последовательные этапы: контекст, планирование, барьер кампании, подготовка,
повествование/проверка, публикация. Барьер не добавляется к подготовке второй раз.

Измеряются вызовы модели, ожидания очереди/приоритета активных ходов, барьер кампании,
выполнение SQL. У запроса есть назначение, схема, модель, размеры входа, доступные токены,
повторы провайдера и их ошибки/длительности. SQL и параметры не сохраняются.
Причины дополнительных запросов обозначают недостающий профиль места, ошибку компиляции
исхода, ремонт повествования, повторную проверку и сетевой повтор.

Сводка считает объединение интервалов. Параллельные операции не суммируются дважды;
вложенные замеренные ожидания вычитаются из времени содержащего их запроса.
При пересечении приоритет категорий: ожидание, SQL, локальная работа, запрос модели.
Полные длительности отдельных строк могут пересекаться, складывать их вручную нельзя.

`unaccounted_ms` — остаток полного времени после объединения измеренных операций.
Названный этап сам по себе не считается объяснением времени. Лимит — 2000 операций
на попытку; превышение показывается как `dropped_intervals` и оставляет время в остатке.
Короткие SQL/ожидания скрываются только в HTML-таблице, но участвуют в расчёте.

## Ограничения

- SQL включает работу драйвера, выполнение запроса и возможное ожидание SQLite.
  Это не доказательство блокировки и не отдельный замер её длительности.
- Commit, получение соединения и прочая пока не размеченная работа
  остаются в явном остатке. Основные операции сборки схем измеряются в новых трассах.
- Для облачного структурированного запроса время провайдера не разделено на TTFT
  и генерацию. Полное время запроса не выдаётся за чистую генерацию модели.
- Токены и длительности отдельных попыток могут отсутствовать, если транспорт
  их не предоставил.

## Экспорт

`llm-performance.jsonl` рядом с DATA_DIR содержит коррелированные запросы и `turn_summary`.
Путь переопределяется `PDM_PERFORMANCE_LOG`. При штатном выходе появляется
`llm-performance.md`: сводка вызовов и попыток, медиана/P95, остаток времени.
При аварийном завершении посреди хода финальная сводка может отсутствовать;
уже записанные запросы остаются в JSONL. Файловая запись выполняется best effort.

API `/api/campaigns/{id}/debugger` возвращает `performance.attempts` и `performance.summary`.
Выборка: последние 100 сводок среди последних 100 generation runs.
Медиана/P95 включают неуспешные попытки и не являются статистикой только публикаций.
Сырые данные доступны также в trace соответствующего generation run.

Диагностика не добавляет запросов к модели, повторов и игровых решений.

## Детальное разложение запроса (новые трассы)

Внутри каждого логического LLM-вызова теперь видны отдельные HTTP-запросы.
Это важно для compatibility fallback: одна попытка получения JSON может отправить
несколько HTTP-запросов с разным форматом. `logical_calls` и `http_requests` считаются
раздельно; дочерний HTTP-интервал не прибавляется к времени содержащего его LLM-вызова.

| Поле HTTP-операции | Что фактически измерено |
| --- | --- |
| `http_request_id`, `parent_id` | Уникальный запрос и родительский логический вызов |
| `request_build_ms` | От начала операции до HTTPX request hook; включает создание/сериализацию запроса |
| `headers_ms` | От начала операции до получения заголовков ответа |
| `headers_wait_ms` | От request hook до response hook; включает транспорт, ожидание сервера и возможную обработку до заголовков |
| `first_line_ms` | Первая декодированная строка потока, включая keepalive; не первый байт TCP |
| `first_event_ms` | Первое успешно разобранное событие; не обязательно текст |
| `first_text_ms` | Первый непустой фрагмент output text; не служебное событие/рассуждение |
| `body_ms` | Получение тела от заголовков до окончания чтения/закрытия потока |
| `after_first_text_ms` | От первого текста до окончания чтения; включает сеть и обработку потока клиентом |
| `wall_ms` | Полное время одной HTTP-операции, включая закрытие response context |

`headers_ms`, `first_event_ms`, `first_text_ms` — накопительные моменты одной временной
шкалы. Их нельзя складывать. Для buffered/non-streaming ответа первого текстового
фрагмента не наблюдается: `first_text_ms=null`, а не 0. Если hook/событие не наблюдалось,
его время также остаётся `null`. Заголовки не подменяются временем получения всего тела.

Внутренняя серверная очередь, prefill и скрытое reasoning по отдельности по-прежнему
**неизвестны**. Поздний первый текст не является доказательством, что всё ожидание ушло
на reasoning. Токены reasoning остаются отдельной usage-метрикой, не секундомером.

Есть локальные интервалы построения wire-схем intent/outcome/profile/travel,
сериализации prompt-схем, подготовки/компактизации provider request, подготовки validator,
декодирования JSON и проверки Pydantic. `call_unaccounted_ms` показывает остаток внутри
логического вызова после объединения измеренных дочерних интервалов. Общий
`unaccounted_ms` всего хода сохраняется; им не прикрывается отсутствующий таймер.

Размер фактического HTTP body (`request_bytes`), размеры prompt/schema, hash схемы,
HTTP status, доступный upstream request ID и **эффективные** reasoning/output settings
записываются без тела промпта, ответа или Authorization headers. `effective_max_tokens=null`
означает, что ограничение не передано в фактическом payload, даже если верхний слой
отдельно сообщает `requested_max_tokens`. Диагностика не изменяет payload ради совпадения этих полей.

### Незавершённые операции и хвост после готовности ответа

JSONL содержит `llm_call_start` и `provider_request_start` до обращения к провайдеру,
а затем завершающие записи. После аварийного завершения можно обнаружить начало без
конца; отсутствующая длительность не становится нулевой. HTTP-повторы имеют разные ID,
но общий parent ID. Ошибка/отмена сохраняет уже наблюдавшиеся заголовки/события/текст.

После готовности ответа `telemetry_flush_start` / `telemetry_flush` отдельно показывают:

- запись usage/decisions и подтверждение её успеха (`usage_saved`, `decisions_saved`);
- `resume_gap_ms` между готовностью ответа и началом flush;
- `server_observed_ms` до окончания flush от начала trace.

Этот хвост не прибавляется задним числом к interactive total. Его записи доступны в
JSONL и Markdown-отчёте; собственное время записи телеметрии не сохраняется рекурсивно
в той же DB-транзакции. `server_observed_ms` не является измерением доставки в браузер.
Сквозное клиентское время по-прежнему следует измерять на стороне клиента.

### Как разбирать медленный ход

1. Найти turn/run/trace, проверить наличие start/end и статус сохранения телеметрии.
2. Сверить число LLM-вызовов и реальных HTTP-запросов. Разобрать каждый дополнительный запрос.
3. Проверить локальную подготовку схем/JSON и `call_unaccounted_ms`.
4. Сравнить заголовки → первое событие → первый текст → конец тела. Так разделяется
   ожидание начала текста и дальнейшее получение, но не выдумывается серверная детализация.
5. Сопоставить output/reasoning/cached-input tokens, размер запроса и эффективные настройки.
6. Проверить SQL/barrier/queue, общий остаток и after-response flush отдельно.

Старые QA-304 трассы не приобретают эту детализацию задним числом: нужен новый замер
той же конфигурации. Добавление наблюдаемости само по себе не заявляет ускорения модели.
