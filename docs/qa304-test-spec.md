## 3. Подготовка и объём

1. Изолированные DATA_DIR, порт и копия профиля авторизации. Основной сервер, сейв и
   профиль пользователя не трогать. Проверить миграцию копии старой БД, сохранить исходную копию.
2. Зафиксировать ОС/железо, настройки всех ролей, actual model, transport, reasoning,
   лимиты контекста/выхода/таймауты, мастера, температуру. Секреты в отчёт не включать.
3. Установить отдельный `PDM_PERFORMANCE_LOG` внутри каталога прогона. Сохранить server log,
   build manifest, настройки без секретов и список версий зависимостей.
4. Выполнить полный deterministic suite по [TESTING-STRATEGY.md](TESTING-STRATEGY.md).
   Это входной контроль, а не доказательство понимания ходов живой моделью.
   Команда из `src/backend`: `PDM_TEXT_PROVIDER=local python -m pytest -q` (POSIX);
   в PowerShell сначала `$env:PDM_TEXT_PROVIDER="local"`, затем `python -m pytest -q`.
   Для длительного soak приложить актуальную mutation-проверку ядра по engineering-rules;
   если внешний runner недоступен, явно отметить NOT RUN, не выдавать coverage за mutation score.
5. Основная конфигурация — реально используемая пользователем связка ролей/провайдера.
   Второй транспорт (ChatGPT plan / облачный API / Ollama) проверять отдельной короткой серией,
   не смешивая его времена с основной выборкой. ChatGPT plan проверять через настоящий transport,
   не подменять его API-key транспортом.

Минимальный содержательный объём:

- A: свежая кампания, 50–60 опубликованных ходов, все положительные цепочки и 30+ ходов continuity.
- B: копия старого сейва, 20–25 опубликованных ходов, миграция, undo, старые события, remote items.
- F: изолированные проверки отказов/отмены/retry — минимум 5 попыток; не портить ими основной сейв.
- Для каждого ещё заявленного поддерживаемого транспорта — 15–20 целевых ходов;
  для локальной модели холодный старт и прогретая серия учитываются отдельно.
- Два контрастных мастера: спокойный/реактивный и инициативный. Не требовать одинаковой прозы.

Живую игру вести **последовательно вручную**: прочитать ответ и trace, затем выбрать следующий ход.
Запрещены заранее отправленная пачка действий, параллельные ходы и rerun-until-green.
Текст примеров ниже адаптировать к фактически созданному миру; ожидаемые инварианты не менять.
Отдельные fault-injection проверки допустимы как контролируемый стенд, но не выдаются за
естественное поведение модели. Если ветка не была достигнута — `NOT EXERCISED`, а не PASS.

### Стартовые условия A

Герой Тарин; присутствуют Борм и торговец Ивен; у торговца собственная сумка,
у героя — другая сумка трав, посох и кошель **с quantity=5**, все явно «при Тарине».
Есть стойка/стол, два похожих документа с разными ID, работа/договорённость с Бормом.
Локации: трактир A, рынок B, контора C. Известен A↔B, путь B↔C ещё не раскрыт.
Есть отдельно закрытый проход и отдельно реально односторонний путь с публично наблюдаемой причиной.
Если мастер не создал эти условия естественно, использовать документированную изолированную
fixture, сохранить её исходный snapshot и отметить способ подготовки. Не объявлять

## 4. Проверки

Для C01–C17 сохранять input → frozen intent → outcomes → execution receipts → authority →
raw draft → проверки/ремонты → публикация → состояние из **новой сессии чтения БД** → memory jobs.
Сравнивать ID и типизированное состояние, не совпадение формулировок. Проза оценивается отдельно.

### C01. Нулевая сессия и стартовый инвентарь

- Создать новую кампанию с тремя вещами «при Тарине» и одной вещью, явно оставленной в комнате.
- После завершения: у переносимых вещей owner_id героя, у оставленной — выбранное место;
  quantity кошелька равен 5. После выхода из комнаты переносимые вещи остаются у героя.
- Отдельно начать без оговорённых физических вещей: «Заметная деталь» и иная вещь-заглушка не появляются.
- Перезапуск приложения не меняет custody и не создаёт повторный стартовый инвентарь.

### C02. Полнота намерения и составные ходы

- «Кладу посох у стойки, достаю серебряк и спрашиваю Борма: когда выходим?»
- «Забираю записку, прощаюсь и иду на рынок. Дорога ведь свободна?»
- Проверить каждое реально заявленное действие и порядок. Конечный вопрос не превращает ход
  в одну реплику; повествование не совершает незаявленные действия за героя.
- Обращение к себе не становится сторонним адресатом. Настоящий адресат выбирается из каста.
- На успешной первой попытке — один логический intent-вызов. Это не требование одного LLM-запроса
  на весь ход: outcome, narrator и validator считаются отдельно, внутренние HTTP-попытки — тоже.

### C03. Реальный strict-schema transport

- Прогнать разговор без действий, обычный переход, blocked action, split, передачу предмета,
  введение NPC и реальный/контролируемый ремонт через используемый cloud transport.
- Не должно быть HTTP 400 invalid_json_schema / `$ref` с запрещённым `description` и бесконечных
  циклов получения валидного JSON. Проверить фактически отправленную схему, не только Pydantic.
- Проверить случаи без предметов, с одним и несколькими предметами; forced-null/empty поля
  не требуют лишнего ответа модели, а восстановленное типизированное значение корректно.
- Отчёт валидатора в текущей версии содержит claims/violations, S-якоря и, при необходимости,
  coverage ремонта. Не требовать старых item_reviews/verdict/summary в wire-ответе модели.

### C04. Маршруты и направления

- Спросить у присутствующего NPC дорогу B→C, получить конкретные направления, пройти туда и вернуться.
  Повторить для уже зарегистрированной локации и для новой, впервые раскрытой в этом ходе.
- Путь становится доступным по реальным ID и переживает сохранение/перезапуск.
- Слух, простое упоминание, условные направления и указания из другой точки не открывают маршрут.
- Обычная дорога обратима. One-way допустим лишь при явной публичной физической причине;
  её evidence должно быть в опубликованных направлениях. Существующая обратная преграда не стирается.
- Если физический переход уже типизированно разрешён, отсутствие старого ребра в графе
  само по себе не превращает его в стену. После публикации маршрут сохраняется.

### C05. Переходы, присутствие и частичный результат

- Поговорить с Бормом **до** ухода и перейти A→B без него: он был present в момент разговора,
  а после перехода остаётся в A. Он не отвечает из B без собственного типизированного перехода.
- Повторить с NPC, который явно сопровождает героя; оба физически перемещаются ровно один раз.
- Составной путь A→B→C, где второй участок закрыт: выполненный префикс A→B не исчезает,
  остановка соответствует реальной преграде. Не создавать новый дубль B.
- Отдельный сценарий с ошибкой провайдера **до публикации**: это полная компенсация незавершённого
  хода, а не опубликованный частичный успех. Не смешивать два разных ожидаемых поведения.

### C06. Количества и split

- Из кошелька 5 достать 1: источник 4, активный child 1 с правильным split_from_item_id.
  Затем достать ещё 2: источник 2, новый split имеет собственную идентичность.
- Во всех шагах суммарное количество активных единиц сохраняется, если расход/создание не разрешены
  отдельным типизированным исходом. Количество не уходит в произвольное текстовое свойство.
- Попытка взять больше остатка не порождает монеты и не делает quantity отрицательным.
- Stale имя «кошель с пятью серебряками» не перезаписывает актуальное typed quantity=2.
- Split сам удовлетворяет item_change; дублирующее quantity-property не вызывает скрытый retry.

### C07. Возврат и объединение монет

- Вернуть split в исходный кошель того же владельца: количество восстанавливается,
  активный лишний child не остаётся. Undo возвращает прежние количество, ID и placement.
- Два последовательных платежа из одного источника одному NPC объединяются с его предыдущими
  единицами этого источника, не создавая бесконечные «серебряк» на каждый платёж.
- Положить кошель на стойку, затем отдельную монету рядом: **общее место и отсутствие владельца
  не разрешают merge**. Кошель и монета остаются разными активными объектами с верными числами.
- Разные владельцы, два одноимённых кошелька, разные источники split: объединения по имени/комнате нет.
- После каждого ответвления проверить БД после публикации, затем после undo и после перезапуска.

### C08. Описание, настоящая передача и отрицательный контроль валидатора

Положительные случаи без ложного ремонта:

- Монета лежит на ладони своего держателя; раскрытый кошель описан у края стойки.
- У торговца своя сумка, у героя своя: похожее описание не перепривязывается к ID сумки героя.
- Обсуждение, воспоминание и условная передача не выдаются за состоявшуюся передачу сейчас.

Обязательные отрицательные случаи:

- Типизированно монета остаётся у героя, но кандидат прозы реально отдаёт её торговцу.
- Без зарегистрированной передачи кандидат утверждает: «Письмо уже в руках Марты» при другом
  подтверждённом holder этого же предмета. Проверить вариант без явного глагола передачи.
- Кандидат называет иного владельца, но claim помечен `static`, `placement` или `past`.

Нельзя получить PASS только из-за метки claim. Для отрицательного контроля сохранить полную
цепочку и доказать, что противоречащая канону проза не опубликована как корректная.
**Риск по коду #296:** static claims исключаются из сравнения. Проверить, что это не создаёт
false negative для утверждения нового владельца того же ID. Не подменять эту проверку тестом,
который вызывает только низкоуровневый item_position_violations, обходя реальный валидатор.
Если такой текст проходит, это дефект, даже если текущие unit-тесты зелёные.

### C09. Ремонт сохраняет результат, а не просто убирает нарушение

- Получить договорённость/ответ с конкретным условием или сроком; прочитать/создать документ;
  разрешить реальный ход мира. Затем проверить ветку ремонта рассказчика.
- После ремонта сохраняются все подтверждённые результаты, текст/свойства документа,
  предметные изменения и допустимый ход мира. Одно «ты остаёшься в комнате» — не успех.
- Сопоставить каждое required outcome с coverage и фактическим абзацем. Пустой/ложный якорь
  и клиентское `_outcomes_verified=true` не доказывают сохранность результата.
- Проверить сочетание свежих S-якорей item claims с P-якорями outcome coverage.
  Если модель отвергла initial draft, но repair валиден, отдельно отметить RAW BAD/PUBLISHED GOOD.
- При отсутствии естественного ремонта провести отдельную обозначенную fault-injection проверку
  плохого первого draft через изолированный harness; реальный validator/repair должны оставаться в цепочке.
  Старый repaired trace без подтверждения coverage не объявлять автоматически GOOD.

### C10. Старый сейв и миграция

- На копии старой БД до typed quantity: проверить миграцию и восстановление запуска без потери сущностей.
- Кошель с legacy quantity=NULL и числом только в старом описании: первый подтверждённый split
  устанавливает количество согласованно; следующий опирается на typed state, а не старое имя.
- Undo/компенсация возвращают исходные количество, owner/location и идентичности.
- Исторические дубли и ранее не созданные документы не должны самопроизвольно «лечиться»
  массовым merge или выдумыванием. Фикс не является миграцией всей старой сюжетной ошибки.

### C11. Компактный audit, S-якоря и удалённые предметы

- В комнате 1/несколько вещей, часть у NPC; в другом месте — большой архив предметов и документов.
  Обычный местный разговор не запускает per-item обход всего удалённого архива.
- Каждый сообщённый claim ссылается на реально существующий S-якорь кандидата и правильный item_id.
  Выдуманный якорь/цитата, чужой ID или несуществующее предложение не подтверждают публикацию.
- Диалог без позиционных утверждений проходит с пустым списком claims.
- Сужение audit не разрешает прозе перенести удалённый документ в карман героя. Проверить
  отрицательный пример и через основной валидатор, и по итоговому опубликованному тексту/БД.
- Добавление удалённых предметов не должно линейно раздувать валидаторный ответ обходом всего inventory.
  Сравнить размеры request/schema/response, а не только число объектов в БД.

### C12. Нити мира, evidence и говорящий

- У NPC есть agenda «потребовать представиться». Представиться и выполнить условие.
  В последующих ходах fulfilled thread закрыт и не требует имени заново.
- Если draft одновременно закрыл нить и предложил её ход, такой ход не исполняется и
  самопротиворечие не оплачивается новым HTTP-вызовом только ради этого исправления.
- Проверить E/A-evidence на фактические источники. Undo источника закрытия возвращает правильный статус нити.
- Отвечает присутствующий человек или реально введённый в этом ходе NPC. Старый знакомый из
  другой комнаты не телепортируется; имя/role не создают дубль. Форма роли не вызывает скрытых повторов схемы.

### C13. Undo и активная история

- Раскрыть маршрут, переместиться, изменить монеты, создать/передать документ, опубликовать событие;
  затем отменить соответствующий ход и спросить о текущем месте/состоянии.
- Предметы, маршруты, one-way-преграды, NPC presence, время и closures откатываются
  в объёме эффектов отменённого хода, без потери предшествовавших изменений.
- События из обеих половин отменённой пары не входят в активный контекст; legacy event без truth_record
  тоже исключён. В аудите история остаётся видимой как inactive/undone.
- Каталог локаций использует последнее **активное** описание, не старейшее и не отменённую прозу.
- Выполнить новый альтернативный ход и перезапустить приложение: отменённая ветка не возвращается.

### C14. Failure → compensation → retry того же user turn

- Отдельно вызвать контролируемый отказ до prepare и после подготовленной передачи/перехода.
  Сохранить состояние до попытки; после отказа проверить его восстановление.
- Повторить через штатный retry **того же** user_turn_id, не посылать новый текст вместо retry.
- Нет UNIQUE action_sequences.trigger_turn_id, повторного расхода монет, двойной передачи,
  дублированных маршрутов/документов или двух опубликованных ответов.
- Компенсированная последовательность уступает место новой; у попыток отдельные trace_id.
  ID generation run не обязан меняться: учитывать attempt и фазу жизненного цикла.
- После успешного retry выполнить undo: отменяется один реально опубликованный эффект.
- Отдельно отменить активную генерацию пользователем. Отмена не превращается в выполненный ход.

### C15. Фоновая память и блокировки

- Сделать несколько ходов с memory jobs, не дожидаться их полного окончания перед следующим ходом.
  Новый фоновый provider call не стартует, пока активен foreground; уже начатый вызов не обязан прерываться.
- Job, уже владеющий барьером, не должен ждать foreground, который сам ждёт этот барьер.
- На изолированном стенде два реальных engine на одном файле SQLite: временно удержать writer,
  затем освободить. Нет взаимной блокировки barrier/SQLite и потери подготовленного состояния.
- Нормальные задержки показываются как реальные waits/SQL, а не приписываются генерации текста.
  Повторяющиеся паузы около busy_timeout=30 с отдельно разбирать, не «лечить» отключением памяти.
- После освобождения фоновые задачи завершаются, не остаются failed/running навсегда;
  память подтверждённого разговора доступна после следующих ходов.

### C16. Новый дебаг и границы измерения

Для обычного, repaired, failed, cancelled и retried хода:

- `/api/debugger` → «Куда ушло время хода» содержит summary, последовательные этапы,
  запросы с назначением, wait/SQL, unaccounted, attempts и доступные токены.
- JSONL, durable `generation_decisions` и debugger согласованы по turn/run/trace/operation IDs.
  После перезапуска завершённые сводки доступны из БД; старые ходы не получают выдуманные замеры.
- По сырым данным сумма exclusive categories + unaccounted равна total с допуском 10 мс.
  Параллельные интервалы и вложенные waits не считаются дважды; фоновые задачи не входят в foreground total.
- Измерить с клиента: submit → первый видимый текст → конец ответа/закрытие потока.
  Отдельно показать разницу client wall и server trace: доставка, UI и финальный flush телеметрии
  не входят автоматически во время модели. Если игрок всё ещё ждёт — этот разрыв не прятать.
- SQL time не называть чистой длительностью блокировки; отсутствующий TTFT/usage не заменять нулём.
- При штатной остановке есть Markdown-сводка. При аварийном убийстве процесса отсутствие
  финальной сводки незавершённого хода допустимо; сохранить частичный JSONL и пометить границу потери.

### C17. Накопление и сочетания

- Через 30+ intervening turns проверить обещание Борма, закрытую нить, два документа,
  местоположение оставленных вещей, обратный маршрут и остаток монет.
- Ещё раз повторить составной ход и разговор после undo/retry. Нельзя пройти короткие cases
  на чистых fixture, но потерять их инварианты при продолжении одной кампании.
- Обязательные цепочки в одной истории:
  1. C01 → C06 → C07 → C08 → C09 → C13: стартовый custody, монеты, repair и undo.
  2. C04 → C05 → C12 → C13 → возврат: маршруты, момент речи, agenda и активная история.
  3. C06 + C04 → C14 → C15 → C16: составной ход, отказ, тот же retry, фон и честное время.

## 5. Производительность — отдельный результат

### P1. Сопоставимые выборки

Минимум 30 обычных прогретых успешных ходов одной конфигурации; отдельно compound/new location,
repair, failure/retry, холодный local start и session zero. Для других транспортов/моделей —
свои строки. Не исключать медленные корректные ходы и не добавлять время раздумий тестировщика.

На ход/попытку: client wall, server total, все phases, logical calls по назначению и роли,
provider attempts/reasons, queue/barrier/SQL, unaccounted, input/cached/output/reasoning tokens
(где доступны), размер schema/prompt/response, длина опубликованного текста, число ремонтов и итог.

### P2. Как объяснить задержку

- Считать медиану/P95, долю отказов и ремонтов; первый успех отдельно от повторных попыток.
- Для пяти самых медленных ходов приложить полный timeline с причинами дополнительных запросов.
- Проверить число вызовов: intent обычно 1, outcome обычно 0/1 (0 лишь для подтверждённого graph fast path),
  profile enrichment условный. World initiative/forced contact могут требовать outcome даже на известном пути.
  Narrator, validator, ремонты и HTTP-повторы не смешивать с числом intent-вызовов.
- Разбирать каждый обычный ход >60 с, каждый SQL/wait >1 с и остаток >max(1 с, 10% total).
  Это пороги расследования, а не доказательство конкретной причины.
- Для retry показать время отдельных попыток и суммарное активное ожидание до одной публикации.
  Отдельно указать сумму длительностей попыток на число публикаций; не называть её медианой.
- Ориентир для обсуждения: median обычного хода ≤30 с, P95 ≤60 с. Это предлагаемые цели,
  не обещание уже достигнутого ускорения и не ранее согласованный SLA. Отметить `TARGET MET/NOT MET`.
  Сохранившиеся 60–90 с нельзя спрятать за общим «тесты прошли».

### P3. Сравнение и цена

QA-302 на `e9d236ea` — исторический ориентир, а не результат текущего main.
Утверждение об ускорении требует одинаковых fixture/моделей/настроек и одного метода подсчёта.
Без такого сравнения отчёт описывает текущий профиль, а не причинный выигрыш каждого PR.
Стоимость по доступной usage учитывать отдельно; API-equivalent оценку для подписочного
транспорта не выдавать за реально списанные деньги. Неполную usage помечать явно.

## 6. Вердикт и критерии приёмки

Три отдельных вывода: **CORRECTNESS**, **PERFORMANCE**, **OBSERVABILITY**.
Итог не может быть «всё хорошо», если один из них FAIL/NOT EXERCISED.

- CORRECTNESS PASS: все обязательные инварианты C01–C17 выполнены; нет потери/дублирования вещей,
  несанкционированного transfer/movement, подмены ID, возвращения отменённой ветки,
  публикации ошибочного исхода или исчезновения заработанного результата после ремонта.
- OBSERVABILITY PASS: завершённые попытки объяснимы по C16, а неизмеренные интервалы/потеря
  данных обозначены честно. Искусственное обнуление остатка именем этапа недопустимо.
- PERFORMANCE: фактические цифры, доля повторов, причины хвостов и достижение предложенных целей.
  Зелёная корректность не означает хорошую скорость. Не сокращать сюжет до пустого fallback ради секунд.
- Системный transport/schema failure, порча состояния, duplicate spend или канонически неверная
  публикация — FAIL с первым неправильным boundary. Стабильная минутная задержка — отдельный
  performance defect. Литературные предпочтения не смешивать с нарушением четырёх запретов.
- Стохастические cases допускают до трёх **заранее обозначенных** независимых попыток на копиях
  fixture. Сохранять все результаты и first-pass rate; известный провал не исчезает после удачного rerun.

## 7. Что передать в отчёте

Каталог `QA304-<code_sha>-<timestamp>/`:

- `REPORT.md`: версия, настройки, матрица C01–C17/P1–P3 с PASS/FAIL/NOT EXERCISED и путями evidence;
  отдельные три вердикта, список новых дефектов и сравнение с прежними симптомами.
- `metrics.json` или CSV: строка на попытку с campaign/user_turn/run/attempt/trace IDs, моделями,
  статусом, timings, counts, tokens, repair/publication mode, клиентским и серверным временем.
- `llm-performance.jsonl`, итоговый `.md`, server log, Runtime/build manifest без секретов.
- Для каждого дефекта: exact input, ожидаемая/фактическая delta, первый неправильный boundary,
  raw/repair/published text, планы, authority, validation findings, receipts, состояния до/после.
- Бэкап БД до начала, после контрольных цепочек, на 50-м ходе и в конце. Снимать согласованно
  SQLite backup API/штатным экспортом, не копировать один `.db` во время WAL-записей.
- Per-turn debugger JSON для контрольных случаев; generation trace также для failed/cancelled,
  у которых нет assistant_turn_id; post-turn jobs после завершения очереди.
- Скриншоты player-visible ошибок и нового latency-блока. RAW/PUBLISHED классификация отдельно
  от сохранности игрового результата; «UNKNOWN» не заменять «GOOD».

Перед длительной игрой выполнить короткие C01–C03, C06–C09, C14–C16.
При системной ошибке остановить продолжение затронутой ветки, сохранить evidence и продолжать
независимые cases на чистых копиях. Не тратить ещё 100 ходов на уже сломанный сейв.
