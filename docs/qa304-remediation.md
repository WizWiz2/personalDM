## Уточнения по исходному отчёту

В архивной БД «Станционный оператор» и «Станционный оператор 2» находятся в разных
локациях: `18bd4325-21a8-4a7c-9be7-3a6c18552c9e` и
`205bcb4d-37d5-412f-9f55-09a4f50a73b6`. Одинаковая роль сама по себе не доказывает,
что это одна личность. Исправление предотвращает неоднозначное создание нового NPC,
но не сливает историю и не переносит существующего человека между этими местами.

Служебная локация, уже созданная старой ошибкой маршрута, также не удаляется автоматически.
Для повторной приёмки нужна копия исходного состояния либо новая кампания.

NOTE-304-A — отсутствие thread surface — остаётся отдельным feature gap, а не
объявляется исправленным вместе с этими дефектами. NOTE-304-B — документированная миграция.

## Обязательные живые цепочки

1. NPC кладёт принадлежащий ему оригинал на стол; игрок кладёт рядом свою копию.
   Проверить обе custody-записи до рассказчика, публикацию без repair-deadlock и сохранность ID.
2. Из кошелька 5 выделить 1, затем 2 единицы; передать одному NPC, попросить убрать.
   Сверять сумму только активных количеств после каждого действия, undo, retry и рестарта.
   Повторить в длинной кампании. Другая вещь из каталога не должна передаваться вместо монет.
3. Создать документ → убрать → A→B→C→A → undo → рестарт → альтернативный ход.
   Проверить точный исходный ID локации, отсутствие документа после undo и целостность БД.
4. Отменить ход, повторить тем же user_turn_id; одна опубликованная пара, один набор эффектов.
5. На изолированном двухпроцессном стенде опросить/перезапустить второй сервер во время
   генерации первого, попытаться отправить второй ввод. Живой run не становится failed;
   вторая генерация не принимается. После настоящего убийства владельца восстановление доступно.
6. Повторно обратиться к известному NPC по роли, затем перейти в соседнее место и вернуться.
   Проверить выбранные cast/location ID. Для действительно нового человека той же профессии
   должно быть самостоятельное основание; без него не создавать нумерованного двойника.
7. На Windows/Python 3.14 повторить исходный sync/compatibility тест и живой ход.
   Сохранить JSONL, durable performance и flush receipts, включая случаи разрыва потока.

Для новой performance-приёмки использовать [разбор времени](turn-performance-debugging.md)
и ТЗ на новый прогон. [#298](https://github.com/WizWiz2/personalDM/pull/298) добавляет
HTTP-замеры; достижение целей 30/60 секунд и ускорение модели здесь не заявляются.
Фиксы не добавляют этапов обращения к модели. Подтверждение живых semantic choices,
нагрузочных хвостов и исходной Windows-ошибки требует нового отчёта.
